## Investigation Summary

The investigation (via `explore` agent) found the following root causes for stuck queues:

1. **`message.process()` has no timeout** — a handler that hangs blocks the prefetch slot permanently
2. **`connect_robust()` has no explicit heartbeat** — default 60s can cause spurious dead connections
3. **`queue.iterator()` has no reconnection/resilience** — consumer loop dies silently on iterator error
4. **No RabbitMQ memory/disk limits** — unbounded queue growth possible
5. **DLX queue declaration fallback may silently drop messages** on PRECONDITION_FAILED
6. **All workers compete on `hrag.retry.requeue`** instead of a single dedicated consumer

## Proposed Remediation Options

### Option A: Conservative (Recommended first)

Add comprehensive logging at every failure point so timeouts and errors are traceable.

#### 1. `message.process()` timeout with logging
**File:** `backend/app/workers/parse_worker.py`

- Wrap the handler call in `asyncio.timeout(30)` (30 seconds)
- On timeout: log `WARNING` with full context (document_id, minio_key, retry_count, queue name)
- On other exceptions: log `ERROR` with same context
- In both cases: **do NOT requeue** (`requeue=False`) so message goes to DLQ via DLX
- Add a `try/except/finally` structure so the logging always fires before the timeout kills the coroutine

```python
# Pseudocode structure
try:
    async with asyncio.timeout(30):
        result = await message.process(delivery)
except asyncio.TimeoutError:
    logger.warning(
        "parse_worker handler timed out",
        extra={
            "document_id": str(document_id),
            "minio_key": minio_key,
            "retry_count": retry_count,
            "queue": queue_name,
        }
    )
    # Do NOT requeue — let DLX handle it
except Exception as e:
    logger.error(
        "parse_worker handler exception",
        extra={
            "document_id": str(document_id),
            "minio_key": minio_key,
            "retry_count": retry_count,
            "queue": queue_name,
            "error": str(e),
            "error_type": type(e).__name__,
        }
    )
finally:
    # Ensure acknowledgment happens regardless
    await message.ack()
```

#### 2. RabbitMQ heartbeat
**File:** `backend/app/queue/connection.py`

- Add `heartbeat=120` to `connect_robust()` call
- Log connection events: `INFO` on connect, `WARNING` on lost connection, `INFO` on reconnect

#### 3. `queue.iterator()` resilience loop with logging
**File:** `backend/app/queue/connection.py`

- Wrap `queue.iterator()` in `while True: try/except`
- On iterator error: log `ERROR` with iterator state, wait 5s, restart
- On successful reconnect: log `INFO`
- Limit restart attempts to avoid infinite loops (log `CRITICAL` and break after 10 failures)

```python
restart_count = 0
while True:
    try:
        logger.info(f"queue_iterator starting", extra={"queue": queue_name})
        async for message in queue.iterator(...):
            # process message
        logger.info(f"queue_iterator exhausted", extra={"queue": queue_name})
        break  # graceful exit
    except Exception as e:
        restart_count += 1
        logger.error(
            f"queue_iterator error",
            extra={"queue": queue_name, "error": str(e), "restart_count": restart_count}
        )
        if restart_count >= 10:
            logger.critical(f"queue_iterator max restarts reached, abandoning", extra={"queue": queue_name})
            break
        await asyncio.sleep(5)
```

#### 4. RabbitMQ queue limits
**File:** `docker-compose.yml` (or `docker-compose.services.yml`)

Add `x-max-length=10000` and `x-overflow=reject-publish` to main queue declarations to prevent unbounded growth.

#### 5. Standardized log fields (all queue components)

Every log entry for queue operations should include at minimum:
- `queue_name` — which queue
- `document_id` — if applicable
- `correlation_id` — if message has one
- `retry_count` — if applicable
- `error_type` — TimeoutError, AMQPError, etc.

Use standard `logging` module (already in use) with `extra={}` dict fields for structured logging so entries are searchable/filterable in Grafana/Loki. No new dependencies needed.

### Option B: Aggressive (In addition to A)
1. Purge old stuck messages from queues (`docker compose exec rabbitmq rabbitmqctl purge_queue`)
2. Add dead-letter queue per worker type (not shared fanout)
3. Add memory/disk limits to RabbitMQ Docker Compose config
4. Implement single dedicated retry consumer (instead of all workers competing)
